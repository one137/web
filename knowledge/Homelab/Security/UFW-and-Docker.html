      UFW and Docker

      UFW and Docker

      Nov 06, 2026

      For the generic UFW setup, see Linux Systems Setup. This is the dockerhost firewall: a host layer (ufw) and a Docker layer on top of it (ufw-docker). Its rules rely on Docker allocating networks inside 172.16.0.0/12 only, which its pinned address pools guarantee (the WireGuard network, 10.100.0.0/24, is set by hand).

      How it fits together

      Docker does not respect ufw. A packet takes one of two paths:

      • Host path: a process on the host itself. Packets go through INPUT, where ufw’s rules live.
      • Docker path: a published container port. A DNAT rule redirects the packet to the container, so it goes through FORWARD and never touches INPUT. ufw deny 443/tcp does nothing to it.

      sudo ss -4 -tulpn tells them apart: ports owned by docker-proxy are on the Docker path.

      PortOwnerPath
      22/tcp, 68/udpsshd, dhclienthost
      172.16.0.1:8090upsnap (UpSnap runs network_mode: host)host
      443, 53, 8025, 22000, 27017, 9443, WG_PORT/udp, 127.0.0.1:11434docker-proxyDocker

      What filters a port depends on how it is exposed:

      • Host path (22, 8090): ufw, step 1.
      • HTTP services, all behind 443: NPM’s access lists, one per proxy host.
      • NPM’s stream hosts (8025, 22000, 27017, WG_PORT): they have no access lists, so only the firewall
      • 53 (Pi-Hole) and 9443 (Portainer): published directly, bypassing NPM, so only the firewall.
      • 11434 (Ollama): bound to loopback, unreachable from outside.

      So steps 2–3 below only matter for the streams, 53 and 9443, and today they only narrow 8025.

      ufw-docker install connects the Docker path to ufw through DOCKER-USER, the chain Docker leaves for user rules in FORWARD. It does two things, both more good practice than necessity here:

      1. Container rules become possible: ufw route rules now govern container ports. The only one in use narrows Mailrise, as defense in depth.
      2. Inbound internet traffic is dropped: RFC1918 sources pass, new connections from anywhere else don’t. This is a second gate behind the router, which already forwards only WG_PORT/udp, so it only matters if more ports ever get forwarded by mistake.

      Because of (2), WireGuard needs an explicit allow. A port forward keeps the source address, so a phone on mobile data arrives with a public IP. Inside the tunnel, peers then arrive as 10.100.0.3 and pass like the LAN.

      Nothing else needs one:

      • LAN: reaches every container port, deliberately (cf. What is deliberately left open).
      • Public web traffic: the Cloudflared tunnel, opened outbound, has a single route to ct-npm:443. It arrives as container traffic, and NPM’s access lists leave it only the public one137.dev host: the site, /comments-api and /clipse-api/.

      Prevent lock-outs

      A mistake can lock out ssh and Portainer at once. Escape hatches:

      1. The Proxmox noVNC console, which ufw cannot touch.
      2. A second ssh session for testing, the first one kept open: an established connection survives most mistakes and proves nothing.

      1. The host layer

      All rules are added before enabling:

      • 10.100.0.0/24: the WireGuard network. Peers arrive as 10.100.0.3, ct-wireguard-easy’s address, as in Nginx Proxy Manager (NPM)‘s access list. Continuous Delivery ssh’s in this way.
      • 8090: NPM reaches UpSnap at docker0’s gateway, so it arrives on INPUT. to any avoids depending on docker0’s address.
      • 68/udp (DHCP client) needs nothing: ufw’s stock before.rules accepts it.

      After this step: the host path only answers ssh (from LAN, WireGuard only) and UpSnap (from Docker networks only). Container ports are untouched, as this layer only governs INPUT: any port opened to 0.0.0.0 by Docker is reachable from anywhere (though only WG_PORT is forwarded from the internet).

      2. The Docker layer

      The block it adds, abridged (sudo iptables -S DOCKER-USER shows the live chain):

      -A DOCKER-USER -j ufw-user-forward
-A DOCKER-USER -m conntrack --ctstate RELATED,ESTABLISHED -j RETURN
-A DOCKER-USER -j RETURN -s 10.0.0.0/8
-A DOCKER-USER -j RETURN -s 172.16.0.0/12
-A DOCKER-USER -j RETURN -s 192.168.0.0/16
-A DOCKER-USER -j ufw-docker-logging-deny -m conntrack --ctstate NEW -d 10.0.0.0/8
-A DOCKER-USER -j ufw-docker-logging-deny -m conntrack --ctstate NEW -d 172.16.0.0/12
-A DOCKER-USER -j ufw-docker-logging-deny -m conntrack --ctstate NEW -d 192.168.0.0/16
      • ufw-user-forward comes first, so ufw route rules win over everything below.
      • Established flows return early: replies to container-initiated traffic are unaffected.
      • Don’t remove -s 172.16.0.0/12: it carries containers’ connections to the LAN, e.g. NPM’s upstreams to proxmox, truenas and the router.
      • Traffic between containers on a shared network never reaches this chain: br_netfilter isn’t loaded (sysctl net.bridge.bridge-nf-call-iptables doesn’t exist), so bridged traffic skips iptables entirely.

      After this step: the LAN and containers still reach every container port (configured in step 3). The internet reaches none, so WireGuard is down from outside until step 3.

      3. Container rules

      • WireGuard: the one public exception. Without it, the tunnel still works from home and only fails from outside.
      • Mailrise: an allow-list, mostly as an exercise, on top of SMTP basic auth. Proxmox is the only sender: TrueNAS alerts go to Telegram directly.
        • The 172.16.0.0/12 allow covers NPM’s own connection to ct-mailrise, which would hit the deny if br_netfilter were ever loaded.
        • WireGuard peers can still reach 10.100.0.4:8025, NPM’s address on their own network: bridged traffic, out of iptables’ reach.

      Rule style:

      • Against the port, with plain ufw. ufw-docker allow ct-npm WG_PORT/udp would pin one rule per ct-npm address, on each of its many networks, and silently break WireGuard when a recreate changes them. to any matches every forwarded packet, containers’ outbound traffic included: fine for 8025 and WG_PORT, which nothing dials out to, but a deny on a port containers use outbound would need narrowing, e.g. with in on <lan-iface>.
      • The port is the container’s (after DNAT), not the published one. All mappings here are 1:1 so it doesn’t matter, but it is a typical source of mistakes.
      • Allows go before the deny they carve out of: ufw matches in insertion order.

      So ufw-docker is used for install only.

      After this step: the internet reaches WG_PORT again, and only that one. The LAN and WireGuard peers still reach every container port except 8025, now limited to proxmox, bar the 10.100.0.4 gap above.

      What is deliberately left open

      Each port below is reachable from the whole LAN and from WireGuard peers.

      PortWhy not narrowed
      53Pi-Hole answers DNS for every client
      443NPM’s access lists already are the per-service ACL; a copy here would drift
      22000Syncthing sync connections are brittle when pinned to addresses
      9443a Portainer lock-out is the worst one. Its login is the real protection: pinning would not stop a compromised admin machine
      27017MongoDB requires authentication and only holds the wiki’s comments
      22same as 9443, with an immediate lock-out risk on the host path

      Narrowing these means tracking addresses against DHCP, for little gain on a flat LAN.

      Verifying

      Everything is expected open except 8025 (unless scanning from proxmox) and 11434:

      • filtered vs closed: no-response is a firewall drop, reset is nothing listening. 11434 reading filtered proves the host default deny is live: Ollama only listens on loopback, so the kernel would otherwise answer with a RST.
      • TTL: ttl 64 for 22, ttl 63 for container ports, one hop further in.
      • Full -p- scans need --max-retries 1 --min-rate 3000, as every closed port now times out. Scan wired: WiFi may rate-limit at that rate and corrupt the results.

      Checks that fail silently, done by hand:

      • dig @192.168.137.13 one137.dev from another LAN host
      • a test notification from Proxmox reaching Telegram, and nc -vz 192.168.137.13 8025 timing out from a WireGuard peer
      • Syncthing still syncing
      • WireGuard from a phone on mobile data
      • a web/ push exercising Continuous Delivery

      Maintenance

      • After systemctl restart docker: check sudo iptables -S DOCKER-USER. If Docker recreated the chain empty, sudo ufw reload restores it.
      • Changing a published port means revisiting these rules by hand.

      Cf. fail2ban, the other half: public traffic comes through the Cloudflared tunnel, where iptables only sees ct-cloudflared, so bans go to Cloudflare’s API instead.
