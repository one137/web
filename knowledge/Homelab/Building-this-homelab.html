      Building this homelab

      Building this homelab

      Nov 04, 2026

      The order this homelab was built in, and the reason each piece has to come where it does.

      Homelab Services lists what runs, Services and network layout draws how any of it is reached, and each note holds its own commands. What is here is the sequence, the reason behind it, and a check at the end of every stage — so a build can stop anywhere along the way and still leave something that works.

      Before starting

      • A domain whose DNS is hosted by Cloudflare. The wildcard certificate is issued by DNS challenge, and the public route is a Cloudflare tunnel, so the zone has to be there before stage 5.
      • One machine for the lab, plus a small always-on one for DNS in stage 4, and somewhere off the premises for a copy of the backups in stage 10. Specs is the machine used here but nothing below depends on that choice.
      • A router that can do three things: serve DHCP with a few static leases, announce a chosen DNS server to its DHCP clients, and forward one UDP port. Nothing else is asked of it.
      • Three free accounts: a Telegram bot and a group for it, where every alert in the lab ends up; a git host for the delivery pipeline in stage 9; and an external check for stage 10.

      The “By topic” list on Homelab covers much of the same ground grouped by subject. It reads better as a table of contents; this page is the route.

      1. The machine and the hypervisor

      Proxmox goes on the small boot drive and leaves the large ones untouched, because stage 2 hands those over whole. The host gets a fixed address on the LAN and the bootstrap every machine here gets: an admin user, keys, ssh hardening, dotfiles. No firewall yet: the only host that runs one is dockerhost, and both its layers come in stage 11.

      The one real hardware hack belongs here too, since only the host can reach the board’s fan controller: a forced driver and a boot-time script pin the case fan at a near-silent speed.

      Two things related to Proxmox but that only come later: scheduled backups (need somewhere to write, stage 2), and notifications (target is a name that does not resolve yet, stages 4 to 6).

      Done when the Proxmox UI answers at its fixed address from the LAN, and after a reboot the case fan reports the speed the script pins it to.

      2. Storage

      TrueNAS runs as a VM, and the data drives are given to it by PCIe passthrough rather than as virtual disks, so ZFS addresses the hardware directly. The pool is created there, then the datasets, the users and the shares (ZFS, Network Shares).

      It starts first of all the VMs, and that start order matters: everything that mounts a share has to come up after it.

      Proxmox’s backups belong to this stage, as soon as there is somewhere to write them: the dumps land on a share of the pool. Getting a copy of that pool off the machine is stage 10’s half of the same job.

      Done when the pool is online, one of its shares mounts from another machine on the LAN, and a file written to it lands with the owner it is supposed to have (a mismatch here surfaces much later, as a container that cannot write to its own volume).

      3. The Docker host

      A Debian VM running Docker — dockerhost everywhere in these notes (Docker). It boots after TrueNAS and waits for it, since several services bind-mount a share. Containers are named ct-..., stacks carry a number that orders them, and every local bind mount lives under one directory owned by one unprivileged user.

      One setting is worth getting right at install time rather than later: Docker’s address pools are pinned to a single range here. The firewall in stage 11 is written against that assumption, and changing it afterwards means recreating every network in the lab.

      The shape of a new service is a rule rather than a judgement each time: Docker when possible, a VM when not, and LXC only to try an OS out. Virtualization records why.

      Portainer comes first and is not itself a stack — it is what deploys the stacks, so it is installed by hand. It also publishes a port of its own, one of the few exceptions to the rule stage 5 sets.

      Done when Portainer opens from the LAN and a throwaway container runs.

      4. Names (DNS)

      Pi-Hole on its own small machine answers DNS for the LAN: the local records that give each machine a name, and the one record that points every *.one137.dev at dockerhost. The router keeps DHCP and the leases, and announces Pi-hole as the DNS server — so DNS and DHCP live in different places, on purpose. A second instance runs on dockerhost for redundancy, but it is a stack like any other and arrives with the rest of them in stage 7; the one on its own machine is what makes DNS survive a dockerhost reboot.

      Names come before the ingress because everything after this is addressed by name. The certificate covers a wildcard name, each proxy host matches a name, and the notification target in stage 6 is a name rather than an address.

      One limit surfaces here and is paid for in stage 8: only one address can be configured per domain, so *.one137.dev cannot answer with dockerhost’s LAN address for a LAN client and with NPM’s VPN address for a remote peer. The fix is a second resolver on the VPN side, not a second record here.

      Done when any x.one137.dev resolves to dockerhost from a LAN client, and the machines (e.g. truenas / truenas.home) resolve by their own names.

      5. One door (the reverse proxy)

      Every service is reached through Nginx Proxy Manager (NPM), and almost no service container publishes a port of its own — the few that do each needed a reason, and Services and network layout lists them with it — so nothing is usable until NPM is. Each hostname gets a proxy host, or a stream host for anything that is not HTTP, pointing at the container by name rather than by address, since container addresses change when a stack is recreated. One wildcard certificate covers every name, issued by DNS challenge through Cloudflare, which is why the domain comes first.

      A single access list, the LAN plus the WireGuard server, guards every proxy host that is not public. Stream hosts cannot have one — NPM offers access lists on proxy hosts only — which is the gap stage 11 exists to close.

      NPM’s stack is numbered 80- even though it is needed this early: it joins the network of every stack it has to reach and declares each one as external, so those networks must already exist when it starts. That numbering is the order for rebuilding, not for building. Starting from nothing, NPM begins with almost no networks and gains one per service, as step 1 of the recipe in Homelab Services describes.

      Done when a proxy host such as proxmox.one137.dev opens from the LAN with a valid certificate. The other half of that check (that it opens from nowhere else) cannot be run yet, since there is no route in from outside until stage 8.

      6. Being told (alerts)

      Mailrise takes SMTP in and sends Telegram out. Proxmox reports by mail only, so Mailrise helps by turning its mails into the same notifications everything else sends. It sits behind a stream host, since SMTP is not HTTP. Obviously it can be used for any other service in the future. TrueNAS needs none of it: its alerts go to Telegram directly, and are set up in this same stage.

      It comes before the bulk of the services for two reasons. Every stage after this one can be verified by watching a message arrive. And the target configured in Proxmox is a *.one137.dev name on a stream port, so the first test message is also proof that stages 4 and 5 did what they claim.

      Done when a test notification sent from Proxmox arrives in Telegram.

      7. The services

      From here it is one service at a time, following the recipe at the end of Homelab Services: a numbered stack with no published ports, its network added to NPM, NPM’s stack redeployed rather than restarted, then a proxy or stream host, then a monitor. The repetition is the point — every service is reached the same way, so there is only ever one place to look. The stack files themselves live in dockerhost-stacks, one per service, linked from each service’s own note.

      The monitoring step of that recipe is the one that cannot be done in order on a first build: the monitor belongs to Uptime-Kuma, which is itself a stage 10 service. The first pass through this stage leaves a list of monitors to add later.

      Service-to-service traffic does not use the front door. A backend dependency shares an internal Docker network with the service that calls it, as MongoDB does with the Comments API, which is both the shorter path and the safer one: no proxy host, so no access list to get right, and nothing that has to be reachable from the LAN (MongoDB’s stream host is only there for mongosh from a laptop).

      Pinned IP addresses lists the few places where an address is written down anyway, and what breaks silently when one of them goes stale.

      Done when every service opens on its own name through NPM, and nothing publishes a host port but the documented exceptions.

      8. Getting in from outside, privately

      Wireguard rather than an exposed service: the router forwards one UDP port to dockerhost, where NPM publishes it and streams it on to the WireGuard server, and a connected peer then behaves like a LAN client. No service is published to make this work: NPM is simply on this path as well, which is the other reason stage 5 comes before this one.

      This is where stage 4’s one-address-per-domain limit is paid off. A peer resolves *.one137.dev through DNSMasq, which answers with NPM’s address on the WireGuard network. The point is attribution, not the shorter path: without it, a peer reaches NPM as a Docker gateway address that no access list can tell apart from a container.

      A home connection’s address changes, so ddclient keeps the Cloudflare record for the WireGuard endpoint pointing at it. That record is the only one in the zone that points home, and the only one Cloudflare cannot (and doesn’t quite need to) sit in front of, since WireGuard is UDP.

      Done when proxmox.one137.dev opens on a phone on mobile data with WireGuard connected, and fails to open with it disconnected.

      9. The public route

      One hostname is public, and it arrives through a Cloudflared tunnel rather than a forwarded port: the connector dials out, so no inbound HTTP port is open anywhere, and the public record points at Cloudflare’s edge rather than at home. The tunnel’s single route targets NPM instead of a service, so public traffic meets the same certificates, access lists and logs as everything else — two ingresses with two sets of rules is the failure this avoids.

      The site itself is static files served by NPM (Public Website, Serve static files through NPM), and Continuous Delivery pushes them in on a commit. That pipeline reaches the host over WireGuard, which is why this stage follows stage 8 and not the other way round.

      fail2ban’s web jails belong here too, because this is the first stage with public traffic worth banning; the ssh jail, on by default in Debian, comes along with them. Those web jails read NPM’s logs and ban through Cloudflare’s API rather than locally: a public request arrives through the tunnel as container traffic, so a packet filter on the host would never see it.

      Done when one137.dev loads from a network outside the LAN, and every other name does not.

      10. Staying up

      Uptime-Kuma watches the containers, the hosts and the public site, and reports to the same Telegram group as everything else. Healthchecks watches Uptime-Kuma from outside the lab, because a monitor that dies quietly is worse than no monitor at all.

      Updates are split rather than shared. Watchtower pulls and restarts by itself, early on one morning of the week, for everything except the handful where an unattended update would be expensive. Diun watches exactly that handful and only reports, a few minutes later, so those are done by hand with a chance to read the release notes first.

      Backups are the other half of staying up. Proxmox dumps the VMs to a share on the pool, an rsync task on TrueNAS copies the pool to a machine elsewhere, and Restic serves the workstations from the same pool — the lab backs them up, not itself.

      Done when stopping a container produces a Telegram message, and silencing the monitor produces one too.

      11. The Docker firewall

      Both layers of dockerhost’s firewall come here, the host layer and the Docker layer, and they wait until last because their rules name the ports that the stages above opened: written earlier, they would be written twice.

      UFW and Docker covers why ufw alone cannot see a published container port, what is deliberately left open, and the lock-out precautions to take before enabling anything. The monitors from stage 10 are no help here: they run on dockerhost itself, so a rule that shuts LAN clients out of a container is invisible to every one of them.

      Done when a scan from the LAN returns exactly the set UFW and Docker documents, and from outside nothing answers but the WireGuard port.

      Not done yet

      To do or explore next is the running list. Some context on its items:

      • Logs and metrics. Uptime-Kuma answers “is it up”. Nothing yet answers “what has it been doing”.
      • Configuration still lives in UIs. Stacks are edited in Portainer and exported by hand, and the ingress is NPM’s database rather than a file in a repo.
      • History off the machine. The copy that leaves is the current state; older versions live only in the pool’s own snapshots.
      • Identity. Access depends on where a request comes from rather than on who is making it.
      • Resilience. One box and one pool: a failure of either is a restore, not a failover.
