      Services and network layout

      Services and network layout

      Oct 18, 2026

      Four questions: how a request gets in, what deliberately does not go through the front door, where the machines and the bytes are, and how a failure gets noticed.

      This page is the map. For what each service is and how it is addressed, see Homelab Services; for the reasoning behind each piece, see the per-service notes linked below.

      Throughout: amber is the ingress point, green is a Docker container, grey is something running directly on a host, blue is a device or service on the LAN, red is outside the homelab. Diagram 3 adds purple for hardware and teal for storage. A dotted edge is a name lookup or a read, not a data path.

      1. How a request reaches a service

      Three ways in, one bouncer. Everything user-facing ends at NPM — the only thing holding certificates and access lists — because service containers publish no host ports, so there is nothing else to talk to.

      1. The public internet, for one137.dev only. Cloudflare terminates TLS at its edge and a Cloudflared tunnel carries the request inward. The tunnel is outbound-only: no inbound HTTP port is open anywhere, and one137.dev’s record points at the tunnel, not home (the only record that does is ddclient’s, for WireGuard).
      2. The LAN, for everything. Pi-Hole answers every *.one137.dev name with 192.168.137.13, so the request lands on NPM’s published :443 directly, without leaving the LAN.
      3. WireGuard, for everything, from anywhere. The router forwards one UDP port and nothing else; a connected peer then behaves like a LAN client.

      Two details the diagram flattens:

      • NPM is on the WireGuard path twice. The router’s UDP port is published by NPM, which stream-forwards it to ct-wireguard-easy; the peer then resolves *.one137.dev through ct-dnsmasq-wireguard to 10.100.0.4 — NPM again, this time on the WireGuard network rather than through dockerhost’s physical interface. That detour is what makes a WireGuard client distinguishable from an ordinary container in NPM’s logs, and it is why the access list can stay as tight as 192.168.137.0/24 plus 10.100.0.3/32.
      • The public route is a single route. Two APIs are served under paths of it rather than on their own hostnames: Comments API at /comments-api and Clipse API at /clipse-api/. Everything else has no public route at all, so fail2ban — which tails NPM’s proxy logs and pushes bans to Cloudflare’s API, since the public path never touches iptables — only ever sees traffic for those three.

      2. What does not go through NPM

      Published host ports

      Each one is an exception that needed a reason. Everything else publishes nothing.

      ContainerPublished onWhy
      ct-npm443, plus the stream portsthe ingress itself
      ct-pihole53/tcp+udp, all interfacesDNS has to answer on the host’s own address
      ct-portainer9443, all interfacesNPM’s own stack cannot be edited through a proxy host on NPM
      ct-ollama127.0.0.1:11434host-local only; containers would use ct-ollama:11434
      ct-upsnaphost network, listens on 172.17.0.1:8090WOL magic packets need the host network, and a host-network container has no DNS record, so NPM targets docker0’s gateway instead

      Couplings between services

      Service-to-service traffic never touches NPM, and should not: access lists match on source IP, and a calling container arrives as a Docker subnet address — broad, and unstable across stack recreates (see Ollama for the long version). It takes three forms, only the first of which is a network path.

      The PCIe passthrough is the load-bearing decision: TrueNAS receives the five data NVMes as whole devices rather than as virtual disks, so ZFS sees real hardware and the pool would survive being moved to another host. Docker persists everything locally under /srv/docker/volumes/ on the dockerhost VM disk — bulk data stays on the pool and comes back in over SMB or NFS. Restic runs the other way round: the server lives on the NAS and the workstations are its clients, so the homelab itself is not what gets backed up there.

      4. How a failure gets noticed

      Every alert funnels into a single Telegram chat.

      Uptime-Kuma carries a Docker monitor per container plus HTTP, DNS and keyword monitors for everything outside Docker, and Mailrise exists because Proxmox can only speak SMTP. Diun reports new upstream images and Watchtower reports what it updated, both on Saturday morning. healthchecks.io watches Uptime-Kuma itself: if the 5-minute ping stops, the alert arrives from outside the homelab — the one failure a self-hosted monitor cannot report on itself.
