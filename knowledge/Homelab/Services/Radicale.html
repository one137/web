      Radicale

      Radicale

      Sep 13, 2026

      CalDAV/CardDAV server for calendars and contacts. Stores one plain .ics/.vcf file per item in a directory tree – no database, so the data is greppable, diffable and trivial to version.

      https://radicale.org

      Setup

      Stack config: https://github.com/one137/dockerhost-stacks/blob/main/stacks/50-radicale.yml

      The image runs as uid/gid 2999 (its own radicale user) instead of dockeruser: its entrypoint rewrites ownership at runtime when given a custom UID/GID, and refuses to do so under read_only. Setting user: "2999:2999" in the stack also makes the entrypoint skip its su-exec path, so the container never runs as root and needs no capabilities at all. Nothing then fixes ownership automatically, so the chown below has to be done before the first start.

      Routing, Monitoring

      Add ct-npm to the 50-radicale_default network and proxy cal.one137.dev / radicale.one137.dev to http://ct-radicale:5232. Set client_max_body_size 100m; in the proxy host’s Advanced tab so a bulk .ics import does not 413.

      If HTTP, the Uptime-Kuma monitor must accept 401, since an unauthenticated request is meant to be rejected. Otherwise use docker container monitoring as usual.

      Use

      Calendars and address books are created from the web UI at https://cal.one137.dev/.web/. It manages collections only – the items inside them come from the clients.

      • iOS: Settings → Apps → Calendar → Calendar Accounts → Add Account → Other → Add CalDAV Account. Server cal.one137.dev is enough, /.well-known/caldav fills in the rest.
      • Android: DAVx5, same base URL, “Login with URL and user name”.
      • Noctalia (Desktop, display only): Settings → Services → Calendar → add a CalDAV account with Server URL https://cal.one137.dev/ – the root, not a collection URL, as it discovers the principal, the calendar home and the collections itself.

      Username / Password are the ones created with htpasswd above.

      Access is the usual LAN + Wireguard access list, so syncing away from the LAN needs the tunnel up. Clients keep a full local copy, so an outage stops syncing but never hides the calendar.

      Versioning and backups

      Every event edit becomes a commit, visible with

      Proxmox backs up the whole VM, which is the right granularity for “dockerhost died” but not for “a client deleted a calendar and synced the deletion to every device”. The commit log covers that second case, and rides along inside the VM image the backup job already captures.

      Notes

      • No iMIP/scheduling: email invitations are neither sent nor parsed. Anything involving outside attendees stays on its own provider.
